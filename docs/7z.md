# Porting the LZMA SDK's 7z decoder

`hivepack-7z` reads 7z archives in safe Rust. It is a port of the 7z decoder of the [LZMA SDK](https://7-zip.org/sdk.html), `C/Util/7z`'s library: opening an archive, listing its files, and decoding its folders. The goal is the one [porting.md](porting.md) sets for zstd: the same results as the library, at its speed.

> **Status:** the whole of the SDK's C decoder: what it opens and what it decodes, with its answers. Past it, as 7-Zip's own program reads them, any graph of coders, with Deflate, Deflate64, BZip2 and the swap filters, Zstandard as 7-Zip's forks write it, and AES with a password. See [What is left](#what-is-left).

## The version

The port follows 7-Zip **26.05**, from `7z2605-src.tar.xz` on the [release's page](https://github.com/ip7z/7zip/releases/tag/26.05), SHA-256 `0b6080b8c3e7a579161d2d495224c0e51c467576cb4c7048b0ab485ef44cc22e` (7-Zip's releases are not signed). `hivepack_7z::UPSTREAM_VERSION` names it.

## The licenses

7-Zip's source release holds code under several licenses, and the port takes care which it reads:

- **`C/`**: `7zArcIn.c`, `7zDec.c`, `Bcj2.c`, `Bra.c`, `Bra86.c`, `BraIA64.c`, `Delta.c`, `Ppmd7.c`, `Ppmd7Dec.c` and `LzmaDec.c`, the files ported, each say at their top that they are in the public domain.
- **`CPP/7zip/`**, 7-Zip's own program, is under the LGPL, its files saying nothing else. None of it is ported. Where this crate goes further than the C decoder, it will follow 7-Zip's behaviour, checked from the outside, not its code.

`hivepack-7z` is under the MIT license, as hivepack is. 7-Zip's program is built only as a tool for the tests (`7zz`), which run it to make archives; it is not linked into anything.

## What following the official code means

The rules of [porting.md](porting.md):

- **The same layout.** Each file becomes a module of a like name: `7zArcIn.c` becomes `arc_in.rs`, `7zDec.c` `dec.rs`, `Ppmd7.c` and `Ppmd7Dec.c` `ppmd7.rs`, `LzmaDec.c` `lzma_dec.rs`, the `Bra*.c` files `bra.rs`, `Bcj2.c` and `Delta.c` `bcj2.rs`.
- **The same names**, in snake case, with the C name in the doc comments: `SzArEx_Open` becomes `Archive::open`, `SzAr_DecodeFolder` `Archive::decode_folder`.
- **The same results.** `Error::number()` is the SDK's `SZ_ERROR_*` number, and `Error::name()` its name. A damaged archive gets the error the SDK gives it, at the same call.

### The differences

- **Folders are readers.** The SDK decodes a whole folder into one buffer, then runs its filter over it, and needs the folder's size in memory: a solid block can be many gigabytes. Here a folder is a reader (`FolderDecoder`), which decodes as much as it is asked for; `Archive::files` reads through it, and `Archive::decode_folder` and `Archive::extract`, the SDK's calls, read all of it into a buffer. The checks are the SDK's, made when each stream ends rather than when the whole buffer is decoded: the same error, reached later when reading in pieces.
- **BCJ2 streams arrive in pieces.** `Bcj2Dec_Decode` sees all four streams whole, in `7zDec.c`. Here each is refilled as it runs out, before each call, so that an empty buffer still means a stream at its end, which is what the decoder's checks rest on.
- **LZMA and LZMA2 are decoded by [`hivepack-xz`](xz.md)**, a port of liblzma's decoders, with the same output, which is already there and faster. On damaged data either may stop at another byte, with the same error. liblzma takes no LZMA properties with `lc + lp` above 4, which the SDK takes, and which 7-Zip makes when asked (`-m0=LZMA:lc=8:lp=4`); `lzma_dec.rs`, the SDK's decoder, reads those. Its dictionary is a ring no larger than the data needs, where the SDK's is the whole output.
- **Memory is limited.** The SDK allocates what the archive says. `Options::memory_limit` bounds the description of the archive, and `Options::decoder_memory_limit` a folder's dictionaries and models, and what `decode_folder` and `extract` keep; past them is `Error::Mem`. Memory for PPMd's model and the dictionaries is zeroed by the system when first touched, so that it costs what is used of it.
- **More than the SDK decodes.** A folder the SDK answers `SZ_ERROR_UNSUPPORTED` to takes another path ([below](#past-the-sdk)). So does any folder of more than 4 coders: the SDK stops at 4 (`SZ_NUM_CODERS_IN_FOLDER_MAX`), and the port at 16.
- **Not ported:** the SDK's `ISzAlloc` allocators and `ILookInStream`, for `Read + Seek`; and the assembly versions of its decoders.

## Past the SDK

The SDK's C decoder takes a few fixed shapes of folder. A folder is really a graph: each coder has input streams, each fed by another coder's output or by a packed stream, and one coder's output is the folder's. `dec.rs`'s `Graph` builds that as a tree of readers, from the unpacked stream back to the packed ones, for the folders `CheckSupportedFolder` refuses, and only for those: the SDK's folders keep its path and its checks. It refuses loops of coders, coders nothing reads, and methods it does not know.

The methods are hivepack's own ports: Deflate and Deflate64 from `hivepack-deflate`, BZip2 from `hivepack-bzip2`, Zstandard from `hivepack-zstd`, with its window limited by `Options::decoder_memory_limit`. BZip2 may hold several streams and Zstandard several frames, one after another.

7-Zip's code for this is under the LGPL, so none of it is ported: what follows comes from `DOC/Methods.txt`, and from asking `7zz t` from the outside.

- **The ends are checked**, as `7zz t` checks them. A coder's stream must end where its output does, and its input must be read to its end: `7zz t` calls more output a data error, and more input an error too (`There are some data after the end of the payload data`), though the data may be right. Here both fail the folder's end, once its data has been read.
- **Zstandard** (`04 F7 11 01`) is not something `7zz` takes in 7z, though 7-Zip has a decoder for it; its forks write it, and libarchive reads it. Its properties, a version, are ignored.
- **AES** (`7zAES`, `06 F1 07 01`), below.
- **The short filter IDs** (`04` for BCJ to `09` for SPARC) are in `DOC/Methods.txt`, which says that xz and 7z share a map of IDs, but `7zz` does not take them in 7z, and neither does the port.

### AES

Password-protected 7z archives use AES-256 in CBC mode, with a key hashed from the password; `-mhe=on` encrypts the headers too, which then need the password to list. `aes7z.rs` is written from the format, as `CPP/7zip/Crypto/7zAes.cpp` is under the LGPL; AES and SHA-256 come from `hivepack-crypto`, which got BearSSL's CBC decryption for this. A coder's properties hold how many times to hash, as a power of 2, a salt and an IV. The key is SHA-256 over the rounds, each the salt, the password in UTF-16LE and the round's number; the power 63 means no hashing, the key being the salt and the password. 7-Zip writes a power of 19, which takes about 30 ms here. Keys are kept for the archive's next folder.

- **Passwords.** `Options::password` opens an archive whose headers are encrypted, and `Archive::set_password` serves one whose names can be read without it. Without one, the data, or the opening when the headers are encrypted, is `Error::PasswordRequired`. `Entry::encrypted` tells which files need it.
- **A wrong password** cannot be told from damaged data, as 7z has nothing to check it with but the data. In an encrypted folder, `SZ_ERROR_DATA` and `SZ_ERROR_CRC` become `Error::WrongPassword`, whose text says it may be either. These two errors are the only ones whose numbers (100 and 101) are not the SDK's, which has no AES.
- **Padding.** The input is whole blocks, the last one padded. `7zz t` takes whole blocks past what the output needs, and refuses a partial one, so the port does too; this one check is looser than the other coders' ends.
- **Rounds.** An archive says how many, and at 7-Zip's limit, a power of 24, each key takes about a second, so `Options::max_key_cycles` lowers it. Past 24, `7zz` goes on without hashing, with a key of zeros, so that any password reads the file; the port answers `SZ_ERROR_UNSUPPORTED`, as nothing writes them.

## How it is shown

The reference is the SDK's own C, built from the release by `scripts/testdata.py` into `tools/7z-oracle`, and archives come from 7-Zip's own program, `7zz`, built from the same release.

- **`tests/oracle.rs`** asks both about each archive, and compares everything: what `SzArEx_Open` returns, every file's name, size, CRC, attributes, times and folder, then what `SzAr_DecodeFolder` returns for each folder and `SzArEx_Extract` for each file, with a hash of the data. The archives are made by `7zz` with 42 sets of options: every method and filter the SDK decodes, BCJ2 in its three shapes, `lc + lp` above 4, end markers, small dictionaries, solid or not, headers compressed or not, with and without times. Each is compared as it is, and damaged 12 times: a bit flipped anywhere, cut short, with more after its end, the packed data changed, or the header changed with its checksums made right again, so that the parsing sees it. Reading with `Archive::files` must give what `extract` gives, and fail where it fails. 546 archives are compared where the oracle is built (Linux and macOS in CI); `testdata/oracle/7z.txt` replays 168 smaller ones everywhere else, including Windows, 32-bit and big-endian machines. Before the first commit, 2,562 more were compared, with other seeds and more damage: no difference.
- **`tests/methods.rs`** checks what the SDK cannot be asked about, against `7zz`. 19 sets of options make archives with those methods, filters on their own or chained, and BCJ2 over mixed methods; they must read back as the files they were made from, both ways. Each is damaged 12 times: whatever `7zz t` calls good must read here too. The reverse may not hold, as the headers are read as the SDK reads them, and 7-Zip's parser is stricter (`Headers Error`). Across 11,400 damaged archives there was no case of `7zz` reading what the port refused, and 11 of the reverse; of the 8 looked at, 7 were a `Headers Error` and one `Cannot open the file as [7z] archive`. Archives put together by hand cover Zstandard, which `7zz` cannot be asked about, a filter alone, a loop of coders, and input and output left over. 10 sets of options make encrypted archives, with a password outside ASCII: they read back with it, are `PasswordRequired` without it and `WrongPassword` with another, and are damaged in the same way. Encrypted archives by hand cover each form of the properties, the padding and the rounds, against `7zz t`.
- **libarchive's test archives**, its 75 `.7z` files, were read before the first commit: all read with their CRCs right but those made malformed on purpose, the encrypted ones with their password.
- **`fuzz/fuzz_targets/sevenz.rs`** opens its input, lists it, reads its files in pieces of all sizes, decodes its folders and extracts its files, with small limits: no panic (see [fuzz/README.md](../fuzz/README.md)). Before the first commit it ran for 15 minutes on 12 cores (5 million inputs), seeded with the recorded archives, with overflow checks and debug assertions on: no panic. It ran as long again with the coder graphs and AES (5 million more), its password and low rounds letting it into the AES coder, with hand-made encrypted archives added to its seeds: no panic. CI's seeds do not hold encrypted archives.

Running the comparisons found what is behind the `lc + lp` difference above: the SDK reads such properties where liblzma refuses them, which damaged headers reach too.

## The speed

`tools/7z-bench` times the port against the SDK's C decoder, and against 7-Zip's program for what that decoder does not read, on archives `7zz` makes:

```sh
python3 scripts/testdata.py fetch --group generated --group bench
cargo run --release -p sevenz-bench -- [--only TEXT] [--rounds 5] [--seconds 0.5]
```

AMD Ryzen 9 9950X (x86-64, Linux), October 2026, the 12 Silesia files cut to 64 MiB in all. Each speed is the best of five rounds taken in turn. "Many" is 100,000 files of 16 bytes with paths for names, and "small" is 5,000 files of 4 KiB, each in a folder of its own. The SDK and `7zz` are built with their makefile's flags, without the assembly decoders that 7-Zip's releases use. Against the SDK, both read the same bytes.

What to read in it:

- **LZMA and its filters** are ahead of the SDK because they go through `hivepack-xz`, liblzma's decoder, against the SDK's C one. 7-Zip's releases have assembly here, which this does not compare with.
- **AES-256 with Copy** is the widest gap. 7-Zip uses the processor's AES instructions, from C (`AesOpt.c`), and is not built without them here; `hivepack-crypto` runs BearSSL's constant-time AES on bitslices, which leaves no secret in the cache or in timing but cannot be fast. Behind a compressor, as in nearly all archives, the gap is small.
- **Each file's name** is not the same work. The SDK copies UTF-16 units into the caller's buffer; `Archive::entries` gives a whole `Entry`, its name also as a `String`, about 110 ns a file. An application listing an archive will not see it.
- **BZip2** is 7-Zip's own decoder, against the port of libbzip2, whose speed `hivepack-bzip2` has ([bzip2.md](bzip2.md)). **Swap4** spends most of its time in the CRC of each file and in reversing bytes, which 7-Zip does with vector instructions.
- **PPMd** stays under the 0.95× the other ports aim at. Its model is read and written through bounds-checked accessors; cutting each read to one check took it from 0.83× to 0.89× at first. A profile puts about a quarter of its time on two lines, the first reads of a context and of its first state, which is where it reaches for memory the model has not touched lately, as the C code does; the rest is spread out, with no single place to gain.
- **`lzma_dec.rs`** is written for what only a few archives need, and not tuned.
- **A folder's CRC** was computed even with none to compare it with, which the first profile found, on Copy and Swap4 above all. Most folders have none, as 7-Zip gives each file a CRC instead.

## What is left

- **`hivepack-open` and `hivepack-extract`**, which will find 7z archives and extract them safely, then packwing.
- **Writing**, once the LZMA SDK's own files have been checked to be in the public domain, as its page says.
