# Porting the LZMA SDK's 7z decoder

`hivepack-7z` reads 7z archives in safe Rust. It is a port of the 7z decoder of the [LZMA SDK](https://7-zip.org/sdk.html), `C/Util/7z`'s library: opening an archive, listing its files, and decoding its folders. The goal is the one [porting.md](porting.md) sets for zstd: the same results as the library, at its speed.

> **Status:** the whole of the SDK's C decoder: what it opens and what it decodes, with its answers. It decodes fewer methods and shapes than 7-Zip's own program, whose code is under the LGPL; see [What is left](#what-is-left).

## The version

The port follows 7-Zip **26.05**, from `7z2605-src.tar.xz` on the [release's page](https://github.com/ip7z/7zip/releases/tag/26.05), SHA-256 `0b6080b8c3e7a579161d2d495224c0e51c467576cb4c7048b0ab485ef44cc22e` (7-Zip's releases are not signed). `hivepack_7z::UPSTREAM_VERSION` names it.

## The licenses

7-Zip's source release holds code under several licenses, and the port takes care which it reads:

- **`C/`**: `7zArcIn.c`, `7zDec.c`, `Bcj2.c`, `Bra.c`, `Bra86.c`, `BraIA64.c`, `Delta.c`, `Ppmd7.c`, `Ppmd7Dec.c` and `LzmaDec.c`, the files ported, each say at their top that they are in the public domain.
- **`CPP/7zip/`**, 7-Zip's own program, is under the LGPL, its files saying nothing else. None of it is ported. Where this crate goes further than the C decoder, it will follow 7-Zip's behaviour, checked from the outside, not its code.

`hivepack-7z` is under the MIT license, as hivepack is. 7-Zip's program is built only as a tool for the tests (`7zz`), which run it to make archives; it is not linked into anything.

## What following the official code means

The rules of [porting.md](porting.md):

- **The same layout.** Each file becomes a module of a like name: `7zArcIn.c` becomes `arc_in.rs`, `7zDec.c` `dec.rs`, `Ppmd7.c` and `Ppmd7Dec.c` `ppmd7.rs`, `LzmaDec.c` `lzma_dec.rs`, the `Bra*.c` files `bra.rs`, `Bcj2.c` and `Delta.c` `bcj2.rs`.
- **The same names**, in snake case, with the C name in the doc comments: `SzArEx_Open` becomes `Archive::open`, `SzAr_DecodeFolder` `Archive::decode_folder`.
- **The same results.** `Error::number()` is the SDK's `SZ_ERROR_*` number, and `Error::name()` its name. A damaged archive gets the error the SDK gives it, at the same call.

### The differences

- **Folders are readers.** The SDK decodes a whole folder into one buffer, then runs its filter over it, and needs the folder's size in memory: a solid block can be many gigabytes. Here a folder is a reader (`FolderDecoder`), which decodes as much as it is asked for; `Archive::files` reads through it, and `Archive::decode_folder` and `Archive::extract`, the SDK's calls, read all of it into a buffer. The checks are the SDK's, made when each stream ends rather than when the whole buffer is decoded: the same error, reached later when reading in pieces.
- **BCJ2 streams arrive in pieces.** `Bcj2Dec_Decode` sees all four streams whole, in `7zDec.c`. Here each is refilled as it runs out, before each call, so that an empty buffer still means a stream at its end, which is what the decoder's checks rest on.
- **LZMA and LZMA2 are decoded by [`hivepack-xz`](xz.md)**, a port of liblzma's decoders, with the same output, which is already there and faster. On damaged data either may stop at another byte, with the same error. liblzma takes no LZMA properties with `lc + lp` above 4, which the SDK takes, and which 7-Zip makes when asked (`-m0=LZMA:lc=8:lp=4`); `lzma_dec.rs`, the SDK's decoder, reads those. Its dictionary is a ring no larger than the data needs, where the SDK's is the whole output.
- **Memory is limited.** The SDK allocates what the archive says. `Options::memory_limit` bounds the description of the archive, and `Options::decoder_memory_limit` a folder's dictionaries and models, and what `decode_folder` and `extract` keep; past them is `Error::Mem`. Memory for PPMd's model and the dictionaries is zeroed by the system when first touched, so that it costs what is used of it.
- **Not ported:** the SDK's `ISzAlloc` allocators and `ILookInStream`, for `Read + Seek`; and the assembly versions of its decoders.

## How it is shown

The reference is the SDK's own C, built from the release by `scripts/testdata.py` into `tools/7z-oracle`, and archives come from 7-Zip's own program, `7zz`, built from the same release.

- **`tests/oracle.rs`** asks both about each archive, and compares everything: what `SzArEx_Open` returns, every file's name, size, CRC, attributes, times and folder, then what `SzAr_DecodeFolder` returns for each folder and `SzArEx_Extract` for each file, with a hash of the data. The archives are made by `7zz` with 42 sets of options: every method and filter the SDK decodes, BCJ2 in its three shapes, `lc + lp` above 4, end markers, small dictionaries, solid or not, headers compressed or not, with and without times. Each is compared as it is, and damaged 12 times: a bit flipped anywhere, cut short, with more after its end, the packed data changed, or the header changed with its checksums made right again, so that the parsing sees it. Reading with `Archive::files` must give what `extract` gives, and fail where it fails. 546 archives are compared where the oracle is built (Linux and macOS in CI); `testdata/oracle/7z.txt` replays 168 smaller ones everywhere else, including Windows, 32-bit and big-endian machines. Before the first commit, 2,562 more were compared, with other seeds and more damage: no difference.
- **libarchive's test archives**, its 75 `.7z` files, were read before the first commit: every method the C decoder supports extracts with its CRCs right, both ways, and the rest (Deflate, BZip2, zstd, AES, some BCJ2 layouts) answer `SZ_ERROR_UNSUPPORTED`, as the C decoder does.
- **`fuzz/fuzz_targets/sevenz.rs`** opens its input, lists it, reads its files in pieces of all sizes, decodes its folders and extracts its files, with small limits: no panic (see [fuzz/README.md](../fuzz/README.md)). Before the first commit it ran for FUZZ_MINUTES minutes on FUZZ_CORES cores (FUZZ_RUNS million inputs), seeded with the recorded archives, with overflow checks and debug assertions on.

Running the comparisons found what is behind the `lc + lp` difference above: the SDK reads such properties where liblzma refuses them, which damaged headers reach too.

## The speed

Reading all of Silesia (212 MB, 12 files) with `Archive::files` on one thread, against `7zz t -mmt=1`, built from the release with its makefile, which leaves out the assembly decoders that 7-Zip's own releases use. Each time is the middle of three runs, on one machine:

| Method | The port | `7zz` | |
|---|---|---|---|
| LZMA, 64 MiB dictionary | 1.43 s | 1.61 s | 1.13× |
| LZMA2, 64 MiB dictionary | 1.43 s | 1.59 s | 1.11× |
| PPMd, order 6, 256 MiB | 12.8 s | 11.4 s | 0.89× |
| LZMA, `lc=5:lp=3` (`lzma_dec.rs`) | 2.08 s | 1.58 s | 0.76× |

`lzma_dec.rs` is written for what only a few archives need, and not tuned. PPMd stays under the 0.95× the other ports aim at. Its model is read and written through bounds-checked accessors; cutting each read to one check took it from 0.83× to 0.89×.

## What is left

- **7-Zip's other methods and shapes**, which the SDK's C decoder answers `SZ_ERROR_UNSUPPORTED` to and 7-Zip's program reads: AES (`7zAES`, which is how password-protected archives are made, sometimes with their headers), Deflate, Deflate64, BZip2, zstd, the swap filters, and any graph of coders rather than the C decoder's fixed shapes. hivepack's other ports already decode most of them.
- **`hivepack-open` and `hivepack-extract`**, which will find 7z archives and extract them safely, then packwing.
- **Writing**, once the LZMA SDK's own files have been checked to be in the public domain, as its page says.
